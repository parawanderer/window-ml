# The hub client (`src/hub/`)

The browser side of [window-ml-hub](https://github.com/parawanderer/window-ml-hub): the cryptography a device needs to
talk to a hub, over WebCrypto. The hub relays ciphertext and routing metadata and can read none of it, so everything
that makes that true lives here.

Nothing in `src/hub/` touches `chrome.*`, so the chat page can use it as the extension does. This is the crypto half;
the websocket client follows.

## Why it is written here rather than only in Rust

The hub has a Rust implementation of the same protocol (`crates/seal`, `crates/client`). Two implementations of a
cryptographic protocol drift in the same places: the HPKE key schedule, and the exact byte layouts of the hello
transcript, the stream frame header and the channel HMAC. So this one was written by the same session that wrote the
Rust one, and the two are checked against each other with vectors in both directions
(`tests/hub-seal.test.mjs`, and window-ml-hub `crates/seal/tests/vectors_ts.rs`).

WebAssembly would remove the duplicate, and it cannot be used: a device's private key is a **non-extractable**
`CryptoKey`, and a WASM implementation would need its raw bytes. That is the property the design rests on, so the
duplicate implementation is the price.

## The pieces

| file | what it is |
| --- | --- |
| `hpke.ts` | RFC 9180 base mode, DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / AES-256-GCM, built from what WebCrypto has |
| `keys.ts` | identities, the certificate chain the hub verifies, the signed hello transcript, and every signing label |
| `seal.ts` | sealed commands and results, wrapped stream keys, published frames, the replay window, keyed channel names |

`src/proto/wmlhub/v1/*.proto` are vendored from the hub and pinned by blob id, generated by `npm run gen-proto` like
the other two schemas.

## What WebCrypto will not do, and what that costs

- **No HPKE.** Hence `hpke.ts`. HKDF's extract and expand are done with HMAC-SHA256 directly, because WebCrypto's HKDF
  does both at once and HPKE needs them apart.
- **No public key from a private one**, and no export of an Ed25519 private key in a format carrying both. A device
  calls `generateIdentity()` and gets both halves, so this only bites when loading a key from a seed (tests and
  vectors): `identityFromSeed` takes the public key as an argument and checks the pair by signing a probe.
- **X25519 has no "public key from private" either**, but it does have the base point, so the public key is
  `x25519(sk, 9)` (`importAgreementKey`).

## Checks, in the order a failure is easiest to read

1. `tests/hub-hpke.test.mjs` runs the RFC's own vector for this suite. If this fails, HPKE is wrong and everything
   below is noise.
2. `tests/hub-seal.test.mjs` opens window-ml-hub's `vectors/seal-v1.json`, vendored and pinned in
   `tests/fixtures/hub/`: the certificates, the hello signature, a sealed command and result, a wrapped key, a frame,
   and the channel names.
3. `scripts/gen-hub-vectors.mjs` writes the vectors for the other direction, which the Rust side opens. Regenerate
   them whenever the format changes:

   ```bash
   node --import tsx scripts/gen-hub-vectors.mjs > ../window-ml-hub/vectors/seal-ts-v1.json
   ```

## Traps

- **A hub is not trusted with anything, including who sent something.** `Envelope.sender` is the hub's word: it is
  bound into the HPKE info, so a ciphertext attributed to anyone else does not open, and what a runtime acts on is the
  signature inside the seal.
- **The checks are in a deliberate order** (sizes, decryption, chain, sender, signature, addressing, clock, scope,
  and the nonce last), so only an authenticated command inside its clock window can occupy a place in the replay
  window. Adding a check in the middle is fine; moving the nonce earlier is not.
- **A key grant travels like any other envelope**, so "this did not open as a command" is not an error to swallow: try
  `openGrant` before deciding something is wrong.
- **`Bytes` is `Uint8Array<ArrayBuffer>`.** WebCrypto refuses bytes that might be backed by a `SharedArrayBuffer`, and
  protobuf decoding hands back the looser type, so decoded fields go through `bytes()` before they reach a crypto call.
