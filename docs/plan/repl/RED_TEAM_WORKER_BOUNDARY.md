# The Python worker's boundary — red-team audit (2026-11-24)

A pass over the boundary between the Python sandbox's realms and everything else: what a worker can post and who judges it, what a cell's text can do on the receiving side, what a full escape into the worker's JS realm would reach, whether a kept finalizer can run code ungated under a lifted call, and what a cell can exhaust outside its own worker. Every claim is either a committed test (named) or a one-line reason why it is not measured. The audit itself was the whole of its first PR (#2144); this revision adds section 3's measured table and the rows section 2 names, committed on the follow-up branch. The open defect's failing rows (redteam-worker-ids.test.mjs) landed on the repair branch the coordinator routed, as redteam-e4's own commits, and pass there un-todo'd once the fix is in.

## 1. What a Python worker can post, and who judges it

The offscreen document's per-worker handler (`src/offscreen.ts:389`) takes seven shapes: a `/files` mount request (`filesMessage`, answered from the run's own channel), `booted`, `partial` (a live stdout chunk), `spending`, `started`, `mlCall`, and the plain result. Judged by EFFECT means the document decides from its own state; trusted means it believes the message. The two fields that would be a capability if trusted are already re-stamped: `marked`/`markSet` are deleted from whatever the worker sent and set from the document's own record (`src/offscreen.ts:455-458`, `py-mark.ts`), and `mlCall`'s client and run come from the pending entry's wire stamp, never from the message (`src/offscreen.ts:433-441`). `started`, `spending` and `booted` only move timers and write housekeeping; the plain result is data for the run that asked.

What is NOT judged is which run a message answers. Every branch resolves the entry as `pending.get(id)` with no check that the posting worker is the one the entry belongs to, and ids are the document's own small sequential counter (`nextId++`). A worker therefore names any pending run: it can ANSWER another principal's run (that run's model sees forged tool output), STREAM into another run's live stdout keyed by that run's streamId (the page shows text the victim never printed), and MAKE another run's `ml` wire call under the victim's client and run id, with the immediate answer posted back to the attacker's worker. This is reachable from a FULL worker, whose realm is never locked down, so its cell can `import js` and call `postMessage` (`tests/python.test.mjs`, "FULL mode leaves the js bridge intact"); a READONLY worker cannot post, because the strip removes `postMessage` and the bridge lift lifts only the `js` refusal, not the strip (`src/python/lockdown.ts`). The agent's own `python_exec` always sends `hardened: true` (`src/sw/sw-python.ts:286`), so the agent path is not exposed today; full mode (the bench/editor) is, and so is anything that bypasses the strip — the premise of item 3.

Rows: `redteam-worker-ids.test.mjs`, three, each with a positive control on the sender's own id; they are redteam-e4's commits on the repair branch, not this PR's. Suggested fix: the handler closes over both `principal` and `entry.principal`; refuse when they differ, before any branch acts on the entry, with the handler's branches enumerated in a table test. Owner: the offscreen/python lane, routed by the coordinator; reported 2026-11-24.

## 2. What a cell's text can do on the receiving side

Stdout, error text, the result value and the streamed chunks reach the page as strings keyed by the run's streamId. The OUTPUT CELL draws them as text, not Markdown: `PlainOutput`/`TimedOutput` build a `<pre class="code"><code class="hljs">` from the string (`src/sidebar/transcript/render-panel.tsx:843`), so a fence printed by Python is never sent to the drawer. A row renders both components with a fence and asserts no diagram, no script element and no event-handler attribute (`redteam-mermaid.test.mjs`, "a cell's stdout is drawn as the code it is"); the doc's "a fence in anything `markdown()` renders" never included the output cell. What IS rendered as Markdown is the text `markdown()` receives — the model's reply, an answer, prose between steps, a live call, the look output — and there `markdown()` escapes the source before any inline markup (`src/sidebar/format.ts`, `text = escapeHtml(mathed)`), and the answer renderer splices only its own tokens into that output (`src/sidebar/transcript/answer-render.tsx`: "user content already escaped"). Two constructs the renderer does trust: KaTeX output, with the default `trust: false` (an `\href` in cell math stays inert), and a ```` ```mermaid ```` fence, which is drawn by the sidebar's mermaid client from the fence's source. The second is now pinned: a fence in text that reaches `markdown()` draws only an `<img>` whose source is a percent-encoded `data:image/svg+xml` URL, even when the cache holds an SVG carrying a `<script>` and an `onload` (the client's gate checks the opening tag and the size, not the body), and the fence's own source is printed as escaped code — no script element and no event-handler attribute reaches the page (`redteam-mermaid.test.mjs`, "a fence reaching markdown() draws only an inert img"). Scratch files are read as data through the reader, and their framing is inert (`tests/attached-files.test.mjs`: a name cannot end the tag).

A registered secret in a LISTING is a real leak: the reader masks file BYTES (`maskSecretBytes`, `src/secret-mask.ts`) but `opendir` returns the shelf's raw name, so `os.listdir("/files/attached/<h>")` prints a value the framed file block would show as `[REDACTED:<NAME>]`. Confirmed by a reader-level row (masked name vs the same file's masked bytes, with a plain attachment as the control). The coordinator ruled it a security repair of #2026; the fix and the row matrix are window-ml session-store's next PR, with the rows mine on that branch, so this audit does not duplicate them.

## 3. What a full escape into the worker's JS realm reaches

The structural fact: the Python worker is `new Worker(chrome.runtime.getURL("python-worker.js"), { name })`, created by the offscreen document (`src/offscreen.ts:371`) — a dedicated worker at the EXTENSION's origin, not a sandboxed frame with an opaque origin. The barrier between a cell and the host is one boot step, `lockdownReadonly` (ses `lockdown()`, the allow-list strip, the bridge gate), not origin isolation. Behind a bypass of that step there is nothing else: the realm is a normal worker on an origin that holds the extension's storage, and the document creates a SharedArrayBuffer for the interrupt buffer at the same origin (`src/offscreen.ts:380`), so shared memory exists there too.

Measured and committed: the allow list and the strip's walk over the real `WorkerGlobalScope` (`tests/python-lockdown.test.mjs` steps 2-3); the bridge gate's refusals and its lift (`tests/python-bridge-gate.test.mjs`); the real worker global after the strip in a browser, four names with the URL constructor as the live control (`tests/e2e/redteam-hard-python-realm.spec.mjs`); the cancel's spend bounds and the flood (`tests/python-spend-queue.test.mjs`); and the outside mark (`tests/redteam-python-outside-mark.test.mjs`, #2115). What a BYPASS reaches is now measured, one row per reach, from a FULL-mode cell (`hardened: false`, the bench/editor path; `redteam-hard-python-realm.spec.mjs`, section "what a BYPASS would reach"). Every row carries the cell's own `Math.max` as the live-global control, so a row cannot pass by the cell never having run:

| Reach from a FULL worker | Reachable | How it was measured |
| --- | --- | --- |
| `chrome.runtime` | no | `_g.chrome` raises `AttributeError: chrome`; the extension's own `dist/devtools.js`, loaded with `importScripts`, runs its body and throws `ReferenceError: chrome is not defined` — a dedicated worker has no `chrome` namespace |
| `chrome.storage` | no | the same absence, probed through `chrome.storage` directly |
| the extension origin's IndexedDB | yes | `indexedDB.databases()` listed `ml-drafts`, `ml-hub-keyring`, `ml-saved-sessions`, `ml-values` |
| the extension origin's OPFS (where the session archive's files live) | yes | `navigator.storage.getDirectory()` returned a directory |
| `fetch` to a third-party host | yes | HTTP 200 from a local server, under the extension's `<all_urls>` |
| `importScripts` of a third-party URL | refused before the network | throws a bare `NetworkError` "failed to load"; the server saw zero requests and the script's global was never set |
| `importScripts` of the extension's own origin | yes | the `devtools.js` body ran (it is the row above's `ReferenceError`) |
| `eval` / `new Function` | refused | `EvalError`: "violates the following Content Security Policy directive … 'unsafe-eval' is not an allowed source of script" |
| `BroadcastChannel` | yes | constructed, posted, closed |

Read with item 1, the shape of the hole is: a bypass gains the extension origin's DATA (the stores above) and outbound `fetch`, but no `chrome.*` API and no way to compile a string; `importScripts` reaches only the extension's own files. The wall is neither an origin boundary (the worker shares the extension's origin) nor the opaque-origin sandbox packages measured — the strip is the whole of the separation, which is what Shane's decision has to weigh. Not measured: other workers' ports (the document's per-worker channel is the only route, and item 1 is that route's boundary) and the archive's SQLite file through OPFS specifically; the OPFS root is reachable, so that is a path/enumeration question, not a reach question. The table is an UPPER BOUND for a bypass: every row was measured from a FULL worker whose global was never stripped. The reverse direction is measured too (ruling 118): a cell in the properly stripped READONLY worker trying to recover a "yes" row through each route a captured reference could open (`redteam-hard-python-realm.spec.mjs`, section "the ROUTE BACK from the strip"; the names it probes are its `NET_IO` constant). A cell that touches the JS bridge is an approved OUTSIDE cell — `import js` is not in the dialect's allow list, so the cell asks and the person approves it — but the strip is the worker's BOOT step, not the dialect's, so every cell in that worker shares the realm these rows measure. Every row carries a live control in the same cell. Rows 0, 0b, 1 and 2 check each "no" against the identical probe in a FULL realm, where it answers "yes"; row 3's names are checked there by the same family probe; row 4 has no FULL control — its "no" is the absence of a host object from the cell's realm, and the argument that a cell-compiled module gets only the imports it passes:

| Route back from a READONLY worker | Recoverable | How it was measured |
| --- | --- | --- |

The FULL realm's identical walk finds `fetch`, `postMessage` and `importScripts` on the prototypes — the control that a walk can see them at all |

Every "yes" row of the table above has its entry point among the 21: OPFS is `navigator` (`navigator.storage.getDirectory()`, and `navigator.locks` and `navigator.serviceWorker` with it, since the whole name is gone), the origin's stores are `indexedDB` and `caches`, the third-party fetch is `fetch`, the own-origin script is `importScripts`, and another context is `BroadcastChannel`, `Worker` or `MessageChannel` |
| Pyodide's own exports: `pyodide_js._module`, `FS`, `loadPackage` (the Emscripten module, its FS, its wasm exports) | no | none of the five names reads through `pyodide_js` in a stripped cell (`lockdown.ts`'s `PYODIDE_JS_SEAL` pops the module out of `sys.modules` and clears its loader's `jsproxy`, so a re-import hands back an empty module), while the same probe in the FULL realm finds `_module`, `FS`, `loadPackage` and `version`; and a sweep of every `pyodide*` module's attributes finds no JsProxy at all in the stripped realm — a JS object a cell could call — against `pyodide_js._module` in the FULL sweep |
| the files mount's channel (a kept `postMessage`/`MessagePort` closure) | no | `postMessage`, `MessageChannel`, `MessagePort`, `addEventListener` and `onmessage` are all absent from the stripped global (the family row), and all five are in `NET_IO`, so the same FULL probe is their control; the relay's `postMessage`/`close` are captured in `lockdownReadonly`'s closure, never on the scope, and the mount is reachable only as a path through `os` |
| a wasm import table (IDBFS, a socket syscall) | no | `WebAssembly` is kept and a cell compiles its own module, but no host `Module`, `wasmModule`, `wasmExports` or `wasmMemory` is reachable, so there is no import table to recover; a module a cell compiles gets only the imports it passes (no FULL control was run, as stated above) |

Read the two tables together: the "yes" rows are what a bypass would gain, and the route back is closed FOR THE ROUTES PROBED, because each "yes" needs a NAME (the strip deletes it) or a REFERENCE (the seal, the closure, the absent host object). The reference walk is now measured, not reasoned: a cell that holds `globalThis` as a JsProxy climbs its prototype chain and every prototype's own names, and finds none of the 21 net/IO names there, with the FULL realm's identical walk as the control; the chain's constructors are readable, and what they yield is measured empty of any live net/IO member, with the CSP refusing `Function` a string. (`import js` is outside the dialect, so that cell is approved as an outside cell; the realm is the same stripped worker's. The JsProxy sweep covers `pyodide*` modules' attributes only.) The strip is what makes the second table empty, so what it leaves a cell is the JS intrinsics it keeps (`WebAssembly`, `crypto`, `TextEncoder`, `structuredClone`, the timers) — an argument from what those intrinsics do, not a row, that none of them reaches the network, the origin's storage or another context without one of the names above. packages' sandbox-page measurement is the comparison: a framed opaque-origin sandbox has no `chrome.runtime`, IDB/OPFS/localStorage/cookie throw SecurityError, parent access throws, fetch is refused with zero server hits unless `connect-src *`, and there is no SharedArrayBuffer, so no interrupt buffer and no SAB files mount. The opaque origin is the thing this design does not purchase; the strip is the whole of its defence.

## 4. An inside-only sequence that runs code ungated under a lifted call

The cross-verdict channel is already closed, by the outside mark: a lifted cell is an OUTSIDE cell (the lift is granted only outside the dialect, `src/sw/sw-python.ts:283-284`), and after any outside cell in a worker no later cell there is tried inside (#2115). A callback planted by approved outside code — `weakref.finalize`, `__del__`, a `gc` callback — therefore cannot be triggered under an auto-approved inside verdict in that worker: the next cell is refused the inside attempt before any code is posted (`src/offscreen.ts:648-652`), and when it runs it runs as an approved outside cell. A finalizer retriggered during later outside cells stays within the verdict that planted it. What the wrapper's cancel does to kept objects' finalizers is documented and tested for tasks (`lockdown.ts`, the cancel's steps 2b and 5); a probe for the kept-namespace case (`weakref.finalize` on an object kept across cells, forced collection in the next cell, assert the outcome and the mark) is the one shape this audit did not run; one-line reason: the mark makes the outcome deterministic for the cross-verdict case, and the intra-outside case needs no new approval. If a probe is wanted, it goes beside `tests/python-spend-queue.test.mjs`'s flood rows.

## 5. What a cell can exhaust outside its own worker

Time and heap are bounded per cell (the 15 s cap swapped in at `started`, the start bound before it, and `memoryKilled`; `tests/python-reap.test.mjs`), and the cancel bounds what a cell left queued. Output floods reach the panel one message per worker flush and are capped in the ring for leased cells (`ringAppend`); the document's own maps are bounded by the runs that exist. Scratch space is `filesQuotaMB` per session, counting stored and pending files across channels (`redteam-files-write.test.mjs`, on #2121's branch). The worst in-budget cell is a bounded loop around a listed C leaf over a large frame: a leaf is one step whatever its input (ruling 106), so the only limits are the clock and memory, and both are the kill's. Not measured: the number of `PY_STDOUT` messages a print loop can force into the service worker; one-line reason: the cost is one `sendMessage` per flush, bounded by the cell's 15 s and the worker's batching, and a bound would need a real worker printing in a loop.

## A note on the 2129 test hook

`__mlLocalToolTextsForTest` (`src/background.ts:179` on #2129) is a global in the service worker's realm, beside the other `__ml*ForTest` hooks. A page cannot reach it: a page's only route into the worker is `chrome.runtime.sendMessage`, which lands in `route()`, an explicit set of type branches with no lookup by global name, and the origin gate refuses every page-started type from an unapproved origin. The hook is reachable only by the extension's own code (e2e calls it through `ext.sw.evaluate`). No pass needed for #2129 on the red-team trigger; the coordinator's ruling stands.
